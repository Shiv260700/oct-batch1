Side 1 · Read the plan, choose the index

Always measure like this

EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
  • EXPLAIN = plan only · ANALYZE = really runs it
  • Data-changing SQL: BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;
  • Run twice. Compare pages (Buffers), not just ms

Read any plan in 5 questions

  1. Start at the most indented node; data flows up
  2. How is the table accessed: Seq Scan or an index?
  3. How many rows thrown away? Rows Removed by Filter
  4. Estimate rows= close to actual rows=?
  5. How many pages? Buffers: shared hit / read

Plan line fields

cost=a..bEstimate in points (not ms): first row..all rows
rows=Planner's guess of rows
actual time=a..bReal ms: first row..last row
loops=NRan N times: multiply rows by N
Index CondIndex did the search
FilterRows checked one by one
Heap FetchesIndex-only scan still visited the table
Batches > 1, DiskRan out of work_mem, spilled to disk

Parent time includes child time: never add node times together.

Will an index help?

  • Few rows of many (e.g. 103 of 1,000,000) → yes
  • Most rows (e.g. 94% SUCCESS) → Seq Scan wins; index ignored
  • An index the planner doesn't use is pure cost

Column order rule: equality columns first → then range / ORDER BY column. Like a phone directory: sorted by surname, then first name.

Indexes are not free

  • Every INSERT/UPDATE must update every index
  • Disk space: check pg_relation_size('idx_name')
  • Unused? pg_stat_user_indexes.idx_scan

Side 2 · Joins, rewrites, functions

Join algorithms

JoinWins whenWatch
Nested LoopFew outer rows + index on innerLarge loops without index
Hash JoinBig equality joinsBatches > 1 (memory)
Merge JoinBoth sides already sortedExtra Sort nodes
  • Foreign keys are NOT indexed automatically. Index the FK column you join or filter on
  • Inner joins: the planner chooses the join order, not you

Correctness traps

  • NOT IN (subquery) returns nothing if the subquery has a NULL → use NOT EXISTS
  • LEFT JOIN + condition in WHERE on the right table = silently an INNER JOIN → put it in ON
  • LIMIT without ORDER BY = random rows
  • Pagination needs a unique tie-breaker: ORDER BY txn_ts DESC, txn_id DESC

Wrong estimates?

  • Estimate far from actual (×10 or more) → the plan may be wrong
  • First: ANALYZE table; (refresh statistics)
  • Related columns (e.g. status & channel):
    CREATE STATISTICS s (mcv) ON status, channel FROM transactions;
  • Look: SELECT * FROM pg_stats WHERE tablename = '...';

Prove the rewrite gives the same answer

SELECT count(*) FROM ((old_query) EXCEPT ALL (new_query)) d;  -- must be 0
SELECT count(*) FROM ((new_query) EXCEPT ALL (old_query)) d;  -- must be 0

Faster but different answer = a bug, not an optimisation.

Functions & procedures

  • Set-based first: one UPDATE beats a LOOP of 10,000 UPDATEs
  • Label volatility correctly: IMMUTABLE (same input → same output, no table reads), STABLE (reads tables), VOLATILE (default, changes data / random)
  • Only IMMUTABLE functions can be used in an index
  • Prefix parameters p_ to avoid clashes with column names
  • Cached (generic) plans can suit one value and hurt another: compare plans for a rare and a busy value
  • Need COMMIT inside? Use a PROCEDURE + CALL

The tuning loop

1 Measure (plan, pages, ms) → 2 find the biggest waste → 3 change one thing → 4 measure again → 5 prove same answer
