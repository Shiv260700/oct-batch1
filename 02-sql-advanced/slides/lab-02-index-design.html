Step 2 · Predict

Same index, two customers

CREATE INDEX idx_txn_payer ON transactions (payer_account);

EXPLAIN (ANALYZE, BUFFERS)

EXPLAIN (ANALYZE, BUFFERS)

Rows are scattered randomly over 12,606 pages, so pages visited = 12,606 × (1 − (1 − 1/12,606)^rows). At 10,216 rows that gives about 7,000, matching the real 7,017.

Step 3 · Predict

We index status. Will it be used?

CREATE INDEX idx_txn_status ON transactions (status);

An index is only as good as the rows it lets you avoid. "The index wasn't used" usually means "the index wouldn't help".

Step 5 · Predict

What if we swap the columns?

BEGIN;
DROP INDEX idx_txn_payer_ts;
DROP INDEX idx_txn_payer;
CREATE INDEX idx_txn_ts_payer ON transactions (txn_ts DESC, payer_account);
EXPLAIN (ANALYZE, BUFFERS)
SELECT txn_id, txn_ts, amount, status FROM transactions
WHERE payer_account = 'u1000@bank' ORDER BY txn_ts DESC LIMIT 10;
ROLLBACK;
A directory sorted by first name, then surname. How fast can you find every "Kumar"?

DROP and CREATE INDEX work inside a transaction. ROLLBACK brings back the good indexes. A safe way to experiment.

Step 5 · See

Wrong order: 50× more pages

Walks the index newest → oldest, checking every entry's payer until it finds 10 for u1000.

Rule

Equality first, then range or ORDER BY

Query patternIndex
WHERE a = ? ORDER BY b LIMIT n(a, b)
WHERE a = ? AND b >= ?(a, b)
WHERE b >= ? only(b): (a, b) won't help much
Put the column compared with = first. Then the index does the sorting for you.

Part 3

Keep the column bare
SARGable filters

Steps 6–7 in the lab guide

Step 6 · Predict

Payments on 15 March: two ways to ask

CREATE INDEX idx_txn_ts ON transactions (txn_ts);

-- A: cast the column
SELECT count(*) FROM transactions
WHERE txn_ts::date = DATE '2026-03-15';

-- B: half-open range on the bare column
SELECT count(*) FROM transactions
WHERE txn_ts >= TIMESTAMP '2026-03-15'
  AND txn_ts <  TIMESTAMP '2026-03-16';
Same answer. Same plan?

The index stores txn_ts values. The query asks about txn_ts::date values, which are not in the index. Rule of thumb: keep the column alone on one side of the comparison.

Why half-open?

>= start AND < next day

txn_ts>= 15 Mar?< 16 Mar?Kept
2026-03-14 23:59:59NoYesNo

BETWEEN '…15' AND '…15 23:59:59' misses 23:59:59.5
Keep the indexed column bare. Move the maths to the other side.

Step 7

Expression index: search by name, any case

CREATE INDEX idx_acc_name ON accounts (holder_name);

SELECT account_id, holder_name, city
FROM accounts
WHERE lower(holder_name) = 'ravi kumar';
 Seq Scan on accounts  (... rows=25)
   Filter: (lower(holder_name) = 'ravi kumar')
   Rows Removed by Filter: 9975
CREATE INDEX idx_acc_name_lower
  ON accounts (lower(holder_name));
 Bitmap Heap Scan on accounts  (... rows=25)
   ->  Bitmap Index Scan on idx_acc_name_lower
         Index Cond: (lower(holder_name) = 'ravi kumar')
Must use a function? Index exactly that expression.

The plain index stores "Ravi Kumar". The query compares "ravi kumar". Different values, so the index is useless until we index lower(holder_name) itself.

A separate notebook listing only the failed payments.

The query's WHERE must match the index's WHERE.

Before the partial index, the plan walked idx_txn_ts backwards and skipped 298 SUCCESS rows. The partial index does the same job with no skipping, 20× smaller, and cheaper to maintain.

Step 9

Covering index: the answer is in the index

SELECT txn_ts, amount FROM transactions
WHERE payer_account = 'u1000@bank' ORDER BY txn_ts DESC;

Before: amount not in any index

 Sort  (... rows=103)
   ->  Bitmap Heap Scan on transactions
         Heap Blocks: exact=103

After: INCLUDE (amount)

 Index Only Scan using idx_txn_payer_ts_amt
   Index Cond: (payer_account = 'u1000@bank')
   Heap Fetches: 0

CREATE INDEX idx_txn_payer_ts_amt ON transactions (payer_account, txn_ts DESC) INCLUDE (amount);

INCLUDE columns are passengers: stored in the index, not used for searching. 4 pages instead of 106, and no sort.

Summary

Which index for which question?

QuestionIndex
Few rows by valueB-tree (payer_account)
Filter keeps most rowsNone: Seq Scan wins
WHERE a = ? ORDER BY b LIMIT nComposite (a, b)
Function on a columnRewrite bare, or expression index
Always the same small slicePartial WHERE status = 'FAILED'
Few columns, skip the tableCovering INCLUDE (amount)
Huge, time-ordered tableBRIN (txn_ts)

Cheat sheet

Index design checklist

  1. Which query needs it? No query → no index.
  2. How selective is the filter?
  3. Equality columns first, then range / ORDER BY.
  4. Is the column bare in the WHERE?
  5. Did the plan change, and did pages go down?
  6. Can an existing index be extended instead?

Avoid these

Common mistakes

  • Indexing every WHERE column
  • Indexing a 94% value
  • Composite columns in the wrong order
  • col::date = …, lower(col) = … with no matching index
  • Partial index WHERE not matching the query
  • Forgetting the write cost
  • Three overlapping indexes "just in case"
