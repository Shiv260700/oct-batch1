Payments per merchant

SELECT m.merchant_account,

Step 2 · Rewrite

Group once, then join

SELECT m.merchant_account,
       COALESCE(c.payments, 0) AS payments
FROM merchants m
LEFT JOIN (SELECT payee_account,
                  count(*) AS payments
           FROM transactions
           GROUP BY payee_account) c
       ON c.payee_account = m.merchant_account;
 Hash Left Join  (... rows=2000 loops=1)
   Hash Cond: (m.merchant_account
               = c.payee_account)
   ->  Seq Scan on merchants m  (rows=2000)
   ->  Hash  (... rows=1950 loops=1)
         ->  HashAggregate  (rows=1951 loops=1)
               ->  Seq Scan on transactions
                     (rows=1000000 loops=1)
 Execution Time: 162.105 ms
transactions scanned once: all 2,000 merchants in 162 ms.
LEFT JOIN + COALESCE(…, 0) keeps the 50 merchants with no payments.

1,951 groups = 1,950 merchants that were paid + 1 group for the NULL payee (pending payments).

Step 3 · Another fix

Or make each repeat cheap: add an index

   SubPlan 1

Important nuance: correlated subqueries are not evil. A repeated full scan is. With an index each repeat costs 0.044 ms.

Step 4 · Prove it

The equivalence template

WITH a AS (     -- original query
    ...
), b AS (       -- rewritten query
    ...
)
SELECT
 (SELECT count(*) FROM
    (SELECT * FROM a EXCEPT ALL SELECT * FROM b) x)
      AS only_in_original,
 (SELECT count(*) FROM
    (SELECT * FROM b EXCEPT ALL SELECT * FROM a) x)
      AS only_in_rewrite;
🧾

Tick two bills against each other both ways: items on bill A missing from B, and items on B missing from A.

EXCEPT ALL also catches a row that appears a different number of times.

The full version with both queries filled in is Step 4 in sql/lab04.sql. Learners reuse this template after every rewrite in this lab.

Step 5 · Predict

Sales per category: when should we group?

-- 5a. Join first, then group
SELECT m.category, count(*), sum(t.amount)
FROM transactions t
JOIN merchants m
  ON m.merchant_account = t.payee_account
GROUP BY m.category;
-- 5b. Group by merchant first, then join
SELECT m.category, sum(s.payments), sum(s.total)
FROM (SELECT payee_account,
             count(*) AS payments,
             sum(amount) AS total
      FROM transactions
      GROUP BY payee_account) s
JOIN merchants m
  ON m.merchant_account = s.payee_account
GROUP BY m.category;

Step 6 · Predict

A CTE totals every merchant. We ask for one.

WITH merchant_sales AS (
    SELECT payee_account,
           count(*) AS payments,
           sum(amount) AS total
    FROM transactions
    GROUP BY payee_account
)
SELECT * FROM merchant_sales
WHERE payee_account = 'merchant7';
Will PostgreSQL total all 1,951 merchants and then keep one, or only total merchant7?

CTE = Common Table Expression = the WITH part. Freshers love CTEs for readability. Good! Now they learn what happens underneath.

Step 6 · See

Default: the filter moves inside the CTE

6a · default (used once → merged)
 GroupAggregate  (... rows=1 loops=1)

         ->  Bitmap Index Scan on idx_txn_payee
               Index Cond: (payee_account = 'merchant7'::text)

6b · WITH merchant_sales AS MATERIALIZED (…)
 CTE Scan on merchant_sales  (... rows=1 loops=1)
   Filter: (payee_account = 'merchant7'::text)
   Rows Removed by Filter: 1950
   CTE merchant_sales
     ->  HashAggregate  (... rows=1951 loops=1)
           ->  Seq Scan on transactions  (... rows=1000000 loops=1)
 Execution Time: 193.134 ms

Default: PostgreSQL merged the CTE into the query and pushed the filter down, so it reads only merchant7's 4,397 rows via the index.

MATERIALIZED: build all 1,951 totals first, then throw away 1,950. 70× slower.

Step 6 · Rules

Inlined or materialized?

ModeWhat happens
Default, used onceMerged; filter pushed down
Default, used twiceBuilt once, reused (CTE Scan ×2)
MATERIALIZEDAlways built first, then filtered
NOT MATERIALIZEDAlways merged, even when used twice
🍲

Materialized = cook the whole buffet, then serve one plate. Inlined = cook just the dish that was ordered.

A CTE is for readability. Let PostgreSQL merge it, unless you have measured otherwise.

Step 6c shows both "used twice" cases with EXPLAIN. Tip: CTE Scan in a plan = the CTE was materialized.

Part 3

Return fewer rows
top-N and pagination

Steps 7–8 in the lab guide

Step 7 · Top-N per group

Latest payment of every payer

7a · row_number() (any database)
SELECT payer_account, txn_id, txn_ts, amount
FROM (SELECT payer_account, txn_id, txn_ts, amount,
        row_number() OVER (
          PARTITION BY payer_account
          ORDER BY txn_ts DESC, txn_id DESC) AS rn
      FROM transactions) ranked
WHERE rn = 1;
7b · DISTINCT ON (PostgreSQL)
SELECT DISTINCT ON (payer_account)
       payer_account, txn_id, txn_ts, amount
FROM transactions
ORDER BY payer_account,
         txn_ts DESC, txn_id DESC;
txn_id DESC is the tie-breaker: two payments in the same second must not pick a random winner.

Read row_number aloud: "number the payments of each payer, newest first; keep number 1".

Step 7 · LATERAL

Latest 3 payments of every merchant

CREATE INDEX idx_txn_payee_ts
    ON transactions (payee_account, txn_ts DESC);

SELECT m.merchant_account,
       last3.txn_id, last3.txn_ts, last3.amount
FROM merchants m
CROSS JOIN LATERAL (
    SELECT t.txn_id, t.txn_ts, t.amount
    FROM transactions t
    WHERE t.payee_account = m.merchant_account
    ORDER BY t.txn_ts DESC
    LIMIT 3
) last3;
🧾

For each shop, take the top 3 receipts from its pile, which is already sorted newest first (the index). No need to sort a million receipts.

LATERAL = "for each row on the left, run this small query". It is a correlated subquery that can return several rows.

Step 8 · Keyset

Remember the last row, continue after it

-- last row of the previous page (row 9,000)
SELECT txn_ts AS last_ts, txn_id AS last_id
FROM transactions
WHERE payer_account = 'u42@bank'
ORDER BY txn_ts DESC, txn_id DESC
OFFSET 8999 LIMIT 1 \gset

-- next page: seek straight past the bookmark
SELECT txn_id, txn_ts, amount
FROM transactions
WHERE payer_account = 'u42@bank'
  AND (txn_ts, txn_id) < (:'last_ts', :last_id)
ORDER BY txn_ts DESC, txn_id DESC
LIMIT 20;

\gset stores the result in psql variables:

  • :last_ts = 2026-01-11 05:57:53
  • :last_id = 114483
In an app, the screen keeps these two values, like a bookmark.
Compare both columns. txn_ts alone skips rows with the same timestamp.

(a, b) < (x, y) is a row comparison: "a < x, or a = x and b < y". It matches the ORDER BY exactly.

Teach the planner that the columns are related

Why care: estimates drive plan choices: join method (Lab 03), index vs scan (Lab 02). A 3× wrong guess can pick the wrong plan. mcv = most common value combinations.

Avoid these

Common mistakes

  • Rewriting without proving
  • JOIN instead of LEFT JOIN: rows vanish
  • COALESCE(max, 0): max of nothing is NULL
  • EXCEPT instead of EXCEPT ALL
  • No tie-breaker in ORDER BY
  • MATERIALIZED "for speed": blocks pushdown
  • Keyset on txn_ts alone: skipped rows
  • EXPLAIN ANALYZE on the 2,000-loop query: over a minute
