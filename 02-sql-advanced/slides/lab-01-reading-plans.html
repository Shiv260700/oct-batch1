The table area is called the heap: rows are in no particular order.

Write 12,606 on the whiteboard. You will come back to it many times.

"Heap" just means "pile": rows are not sorted by customer.

Analogy

An index is the index at the back of a book

No index

Read all 500 pages

Look at every page to find the word "UPI".

= Sequential Scan

With index

Check the back: "UPI → p. 212"

Open only page 212.

= Index Scan

An index is a sorted list of values + the location of each row.

Everyone knows a book index. Hold onto this picture; Lab 02 extends it (phone directory for composite indexes).

Big picture

SQL says what. The planner decides how.

Your SQL"payments of u1000"
→
Plannerprices every possible way, picks the cheapest
→
Plan"scan the whole table"
→
Executorruns the plan, returns rows

EXPLAIN

Shows the plan. Does not run the query.

EXPLAIN ANALYZE

Runs the query and shows plan + real measurements.

The planner uses statistics about the data (gathered by ANALYZE) to estimate how many rows each step will produce.

Step 5 · BUFFERS

Count the pages, not just the milliseconds

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM transactions
WHERE payer_account = 'u1000@bank';
   Rows Removed by Filter: 999897
   Buffers: shared hit=12606
 Execution Time: 36.569 ms

12,606 = every page of the table.

🗄️

hit = file already on your desk (in memory)
read = fetched from the cupboard first

Always use (ANALYZE, BUFFERS). Time changes run to run; pages don't.

Run the query twice. Time differs; buffers stay at 12,606. That is why pages are the honest measure of work.

Part 3

The plan tree
read it bottom-up

Step 6 in the lab guide

Step 6 · Predict

FAILED payments per channel

EXPLAIN (ANALYZE, BUFFERS)
SELECT channel, count(*) AS failed
FROM transactions
WHERE status = 'FAILED'
GROUP BY channel
ORDER BY failed DESC;
Three jobs: scan, group, sort. In which order? How many rows come out of each?

Step 6 · See

Data flows up from the deepest line

 Sort  (... actual time=46.105..46.106 rows=3 loops=1)                 ③ sort 3 rows
   Sort Key: (count(*)) DESC
   ->  HashAggregate  (... actual time=46.101..46.101 rows=3 loops=1)  ② group into 3
         Group Key: channel
         ->  Seq Scan on transactions  (... rows=48998 loops=1)        ① read + filter
               Filter: (status = 'FAILED'::text)
               Rows Removed by Filter: 951002
 Execution Time: 46.117 ms
-> means "feeds into the line above".
Parent time includes its children. Never add times together.

Reveal ① first, then ②, then ③. Ask: why does the Sort take 46 ms if it only sorts 3 rows? Because its time includes everything below it.

Step 6 · Picture

A funnel: rows shrink as they move up

Sort → 3 rows
▲
HashAggregate → 3 rows
▲ 48,998 rows
Seq Scan reads 1,000,000 · keeps 48,998

Where did 48,995 rows go?

They were not thrown away. They were summarised into 3 counts.

Filter removes rows. Aggregate summarises rows.

PostgreSQL creates an index for every PRIMARY KEY and UNIQUE constraint automatically. That is why this was fast without us doing anything.

Read the difference

Index Cond vs Filter

Index Cond

The index did the searching

Jumps straight to matching rows.

Few pages read.

Filter

Rows checked one by one

Reads rows first, then throws non-matches away.

Look for Rows Removed by Filter.

This one distinction lets freshers diagnose most slow lookups. Ask them to find "Index Cond" or "Filter" in every plan for the rest of the workshop.

Step 8 · See

A Bitmap scan: two steps

 Bitmap Heap Scan on transactions  (... actual time=0.023..0.128 rows=103 loops=1)
   Recheck Cond: (payer_account = 'u1000@bank'::text)
   Heap Blocks: exact=103
   Buffers: shared hit=103 read=3
   ->  Bitmap Index Scan on idx_txn_payer  (... rows=103 loops=1)
         Index Cond: (payer_account = 'u1000@bank'::text)
         Buffers: shared read=3
 Execution Time: 0.140 ms
① Bitmap Index Scan

Search the index → list of 103 row locations (3 pages)

② Bitmap Heap Scan

Visit those 103 table pages, in page order

Most people predict "Index Scan". Bitmap is PostgreSQL's choice when rows are spread over many pages; the next slide explains why.

Why "Bitmap"?

Collect all locations first, then visit each page once

🛒

A shopping list sorted by aisle: you walk the shop once, in order, instead of running back and forth.

Index → 103 locations (page 17, page 9 044, page 233, …)
▼ sort by page number
page 17, page 233, …, page 9 044
▼ read each page once, in order
103 rows returned

Our 103 rows live on 103 different pages (payments are stored in time order, not by customer). Bitmap avoids jumping randomly back and forth.

The index helped because we wanted very few rows: 103 out of 1,000,000.

Emphasise "same answer". A tuning change that changes the result is a bug, not an optimisation. Lab 04 makes this a habit.

Summary

Three ways to read a table

Seq Scan

Read every page

Best when you need many rows, or there is no useful index.

Index Scan

Jump to the row

Best for one or a few rows, e.g. by primary key.

Bitmap Scan

Collect, then visit

Best for a moderate number of rows spread over many pages.

Lab 02 shows when PostgreSQL deliberately chooses Seq Scan even though an index exists.

Step 10 · Safety

EXPLAIN ANALYZE really runs the statement

BEGIN;
EXPLAIN ANALYZE
UPDATE transactions SET status = 'FAILED'
WHERE txn_id = 1;

SELECT status FROM transactions
WHERE txn_id = 1;          -- FAILED: changed!

ROLLBACK;                  -- undo
Safe

EXPLAIN: plan only

Runs for real

EXPLAIN ANALYZE on UPDATE / DELETE / INSERT

Wrap it in BEGIN; … ROLLBACK;

Tell a story: someone ran EXPLAIN ANALYZE DELETE on production "just to see the plan". Don't be that person.

Cheat sheet

Read any plan in 5 questions

  1. Which node is most indented? Start there.
  2. How does it access the table: Seq Scan or an index?
  3. How many rows are thrown away? (Rows Removed by Filter)
  4. Is the estimate (rows=) close to the actual rows?
  5. How many pages? (Buffers)

This is on the printed cheat sheet. Use these 5 questions in every later lab.

Avoid these

Common mistakes

  • Reading cost as milliseconds
  • Reading the plan top-down
  • Adding node times together
  • Forgetting loops=3
  • Trusting a single timing run
  • EXPLAIN ANALYZE DELETE without ROLLBACK
