Step 2

Wrap the query in a function

CREATE FUNCTION get_payments(
    p_payer text,
    p_limit int DEFAULT 5)
RETURNS TABLE (txn_id bigint, txn_ts timestamp,
    amount numeric, status text, merchant_name text)
LANGUAGE sql
STABLE
AS $$
    SELECT t.txn_id, t.txn_ts, t.amount, t.status,
           m.merchant_name
    FROM transactions t
    LEFT JOIN merchants m
           ON m.merchant_account = t.payee_account
    WHERE t.payer_account = p_payer
    ORDER BY t.txn_ts DESC
    LIMIT p_limit;
$$;
p_payer textInput parameter
DEFAULT 5Optional, like limit=5
RETURNS TABLEReturns rows: use it like a table
LANGUAGE sqlBody is plain SQL
STABLEReads data, never changes it
$$ … $$Quotes around the body

The body is exactly the Step 1 query, with 'u1000@bank' replaced by p_payer and 5 by p_limit. Nothing else changed.

Inlining works for simple LANGUAGE sql functions: one SELECT, STABLE or IMMUTABLE, not STRICT, not SECURITY DEFINER. For PL/pgSQL, copy the inner query and EXPLAIN it (Try-it T5).

Step 4

Anatomy of a PL/pgSQL function

CREATE FUNCTION payment_summary(p_payer text)
RETURNS text LANGUAGE plpgsql STABLE AS $$
DECLARE
  v_total int; v_failed int; v_level text;
BEGIN
  PERFORM 1 FROM accounts WHERE account_id = p_payer;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'Unknown payer: %', p_payer;
  END IF;
  SELECT count(*),
         count(*) FILTER (WHERE status = 'FAILED')
  INTO v_total, v_failed
  FROM transactions WHERE payer_account = p_payer;
  IF v_total = 0 THEN                v_level := 'NEW';
  ELSIF v_failed * 10 > v_total THEN v_level := 'CHECK';
  ELSE                               v_level := 'OK';
  END IF;
  RAISE NOTICE 'payer %: % payments', p_payer, v_total;
  RETURN p_payer || ' | ' || v_level;
END; $$;
  1. DECLARE: variables (v_)
  2. Validate: PERFORM + FOUND
  3. Query INTO variables
  4. Decide: IF / ELSIF / ELSE
  5. Tell: RAISE NOTICE
  6. Answer: RETURN

Read it as a recipe: declare, validate, fetch, decide, tell, answer. This is a shortened version; the full one (with amount paid and a HINT) is in sql/lab06.sql.

Step 5

RETURN QUERY and try / except

Validate, then return rows

BEGIN
    IF p_limit NOT BETWEEN 1 AND 100 THEN
        RAISE EXCEPTION 'p_limit must be 1..100, got %',
              p_limit;
    END IF;

    RETURN QUERY
        SELECT * FROM get_payments(p_payer, p_limit);

    IF NOT FOUND THEN
        RAISE NOTICE 'No payments for %', p_payer;
    END IF;
END;
NOTICE:  No payments for u9950@bank
ERROR:   p_limit must be 1..100, got 500

Catch an error

BEGIN
    RETURN payment_summary(p_payer);
EXCEPTION
    WHEN others THEN
        RETURN 'error: ' || SQLERRM;
END;
 error: Unknown payer: nobody@bank
Validate early. Catch errors only where you can do something useful.

RETURN QUERY appends rows and keeps going; the function ends at END. SQLERRM is the message text, like str(e) in Python.

Part 3

Volatility
a promise to the planner

Step 6 in the lab guide

Step 6

Three promises

IMMUTABLE

🧮 A calculator

Same input → same output, forever. Reads no tables.

upper(), maths, clean_name()

STABLE

🏦 Today's balance

Same output within one query. May read tables.

now(), get_payments()

VOLATILE

🎲 A dice roll

Can change every call, or changes data. The default.

random(), anything with UPDATE

The label tells the planner what it may cache or pre-compute. The planner believes you; it does not check.

Step 6 · See

IMMUTABLE functions can be indexed

CREATE FUNCTION clean_name(p_name text) RETURNS text
LANGUAGE sql IMMUTABLE AS $$ SELECT lower(trim(p_name)) $$;

... WHERE clean_name(holder_name) = clean_name('  RAVI Kumar ');   -- 25 accounts

Before

 Seq Scan on accounts (... rows=25 loops=1)
   Filter: (lower(TRIM(BOTH FROM holder_name))
            = 'ravi kumar'::text)
   Rows Removed by Filter: 9975

After CREATE INDEX … (clean_name(holder_name))

 Bitmap Index Scan on idx_acc_clean_name
   Index Cond: (lower(TRIM(BOTH FROM holder_name))
                = 'ravi kumar'::text)
 Execution Time: 0.034 ms

An expression index stores clean_name(holder_name) for every row, computed in advance. That is only safe if the result can never change, hence IMMUTABLE.

Step 6 · Watch out

Lying about volatility gives wrong answers

CREATE INDEX idx_acc_bad ON accounts (clean_name_stable(holder_name));
ERROR:  functions in index expression must be marked IMMUTABLE
PostgreSQL protects you

STABLE / VOLATILE functions cannot be indexed.

…unless you lie

Mark a table-reading function IMMUTABLE → the index keeps old answers. No error, just wrong rows.

Label honestly. Unsure? STABLE for reads, VOLATILE for writes.

Story: someone marks get_category(merchant) IMMUTABLE and indexes it. The merchant later changes category; the index still has the old one. Queries silently return wrong rows.

Three performance traps

Steps 7–9 in the lab guide

Step 7 · Predict

The index on payer_account exists. Which is fast?

-- A: function on the COLUMN
SELECT count(*) FROM transactions
WHERE clean_name(payer_account) = 'u1000@bank';

-- B: function on the VALUE
SELECT count(*) FROM transactions
WHERE payer_account = clean_name('  U1000@BANK ');
Both return 103. Will both use the index to search?

Step 7 · See

Trap 1: a function on the column

A · function on the column

   ->  Index Only Scan using idx_txn_payer on transactions  (... rows=103 loops=1)
         Filter: (lower(TRIM(BOTH FROM payer_account)) = 'u1000@bank'::text)
         Rows Removed by Filter: 999897
 Execution Time: 187.237 ms

B · function on the value

   ->  Index Only Scan using idx_txn_payer on transactions  (... rows=103 loops=1)
         Index Cond: (payer_account = 'u1000@bank'::text)
         Buffers: shared hit=4
 Execution Time: 0.029 ms
Put the function on the value, not the column. (Or build an expression index.)

A uses the index only as a list to read end to end, running the function 1,000,000 times. Remember Lab 01: Filter = checked one by one; Index Cond = the index searched. 187 ms vs 0.03 ms.

Step 8 · Predict

A summary row for every account

A · loop (10,000 times)

FOR r IN SELECT account_id FROM accounts LOOP
    SELECT count(*), coalesce(sum(amount), 0)
    INTO v_count, v_paid
    FROM transactions
    WHERE payer_account = r.account_id
      AND status = 'SUCCESS';

    INSERT INTO customer_totals
    VALUES (r.account_id, v_count, v_paid);
END LOOP;

B · one statement

INSERT INTO customer_totals
SELECT a.account_id,
       count(t.txn_id),
       coalesce(sum(t.amount), 0)
FROM accounts a
LEFT JOIN transactions t
       ON t.payer_account = a.account_id
      AND t.status = 'SUCCESS'
GROUP BY a.account_id;
Same 10,000 rows. Which is faster, and by how much?

Both run inside BEGIN ... ROLLBACK with \timing on. Ask the room: who has written loops like A in Python plus SQL? Most hands go up.

Step 8 · See

Trap 2: row-by-row thinking

644 ms
A · loop: 10,000 queries + 10,000 inserts
246 ms
B · one statement
🛒

A = 10,000 trips to the shop, one item each. B = one trip with the full list.

That's with an index. Without one, A scans the table 10,000 times.
Think in sets. Loop only when each row needs different logic.

Step 9

Trap 3: one saved plan for every value

PREPARE by_status(text) AS
  SELECT count(*), sum(amount)
  FROM transactions
  WHERE status = $1;

EXECUTE by_status('PENDING');   -- 1%
EXECUTE by_status('SUCCESS');   -- 94%

PL/pgSQL functions save plans for their queries the same way.

Custom plan

👔 Tailor-made: built for the actual value.

Generic plan

👕 One size fits all: built once with $1, without knowing the value.

Default plan_cache_mode = auto: the first 5 executions get custom plans; after that PostgreSQL may switch to the generic plan if it looks about as cheap.

Step 10 · Run

Expire old PENDING payments in batches

CREATE OR REPLACE PROCEDURE expire_pending(
    p_before timestamp, p_batch int DEFAULT 2000)
LANGUAGE plpgsql AS $$
DECLARE v_rows int; v_batch int := 0;
BEGIN
  LOOP
    UPDATE pending_queue SET status = 'EXPIRED'
    WHERE txn_id IN (SELECT txn_id FROM pending_queue
                     WHERE status = 'PENDING'
                       AND txn_ts < p_before
                     LIMIT p_batch);
    GET DIAGNOSTICS v_rows = ROW_COUNT;
    EXIT WHEN v_rows = 0;
    v_batch := v_batch + 1;
    COMMIT;                    -- save this batch
    RAISE NOTICE 'batch %: % rows expired',
                 v_batch, v_rows;
  END LOOP;
END; $$;

CALL expire_pending('2026-03-01');
NOTICE:  batch 1: 2000 rows expired
NOTICE:  batch 2: 2000 rows expired
NOTICE:  batch 3: 2000 rows expired
NOTICE:  batch 4: 651 rows expired

 EXPIRED |  6651
 PENDING |  3328

Runs on pending_queue, a copy of the 9,979 PENDING payments, so the real data stays unchanged.

GET DIAGNOSTICS ... ROW_COUNT = how many rows the last statement touched. The loop stops when a batch finds nothing to do.

Step 10 · Why batches?

Small transactions, short locks

📦

Moving house box by box: if you stop halfway, every box already moved stays moved.

Batches + COMMIT
  • Locks held briefly
  • A crash loses one batch only
  • Progress visible to others
A function cannot do it 
SELECT try_commit();
ERROR:  invalid transaction termination

Also: CALL expire_pending inside your own BEGIN ... ROLLBACK fails with the same error, because the procedure cannot commit a transaction it doesn't own.

Step 11

Name parameters p_, variables v_

Parameter named like a column

...
    RETURN (SELECT count(*) FROM transactions

ERROR:  column reference "payer_account"
        is ambiguous
DETAIL:  It could refer to either a PL/pgSQL
         variable or a table column.

Fixed

CREATE FUNCTION count_payments(p_payer text)
RETURNS bigint LANGUAGE sql STABLE STRICT
AS $$ SELECT count(*) FROM transactions
      WHERE payer_account = p_payer $$;

SELECT count_payments('u1000@bank');  -- 103
SELECT count_payments(NULL);          -- NULL
STRICT: any NULL input → NULL out, the body never runs.

Cheat sheet

Function checklist

  1. Can it be one SQL statement? Then don't loop.
  2. Correct volatility label?
  3. Parameters p_…, variables v_…, columns qualified?
  4. Inputs validated, clear error messages?
  5. Function on the value side of WHERE, not the column?
  6. Tested with a busy and a rare value?
  7. SECURITY DEFINER? Runs with the owner's rights: set search_path, grant narrowly.

SECURITY DEFINER gets one sentence only: it's powerful and risky; treat it like sudo.

Avoid these

Common mistakes

  • Looping over rows for work one statement can do
  • Leaving everything VOLATILE, or IMMUTABLE on a table-reading function
  • WHERE my_func(column) = value
  • Parameter named like a column
  • COMMIT inside a function
  • Trusting Function Scan in EXPLAIN
  • Testing with one value only
