Rules of the game

Six rules

  1. Baseline first. Run all 4 queries before changing anything.
  2. One change at a time: an index or a rewrite.
  3. Measure with EXPLAIN (ANALYZE, BUFFERS): ms and pages.
  4. Prove the answer with the "same answer?" check (helper H2).
  5. A changed answer is a bug, unless you prove the old one was wrong.
  6. Write it down on the scorecard. You will present it.

Rule 5 is the twist of this lab: one panel's old answer IS wrong. Teams must prove it, not just claim it.

Debrief · Q3

Why NOT IN returned nothing

SELECT count(*) FROM transactions
WHERE payee_account IS NULL;
--  1982

Some PENDING payments have no payee yet.

ExpressionResult
'm1951' NOT IN ('m1','m2')TRUE
'm1951' NOT IN ('m1','m2', NULL)NULL → row dropped
One NULL in the list → NOT IN returns no rows. Use NOT EXISTS.

"Is merchant 1951 different from NULL?" SQL answers "unknown", and WHERE keeps only TRUE. So every merchant disappears.

On a busy payments system, which index would you drop first? What gets slower?

No single right answer. Good answers: replace the Q1 B-tree with BRIN; use Option A for Q2 (no index) if the table is write-heavy; keep Q4's index because a customer screen needs it.
