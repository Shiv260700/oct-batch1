SQL Performance Workshop · Lab 03

Joins

Three ways PostgreSQL combines tables,
and three traps that give wrong answers.

Lab 03 has two halves: speed (which join method, which index) and correctness (LEFT JOIN, NOT IN). Both come up daily in real jobs.

The story

"Show the merchant names too"

Support wants u1000@bank's payments with merchant names.

SELECT t.txn_id, t.amount, m.merchant_name
FROM transactions t
JOIN merchants m
  ON m.merchant_account = t.payee_account
WHERE t.payer_account = 'u1000@bank';
And managers want
  • Spend per merchant category
  • Top corporate customers per city
  • Merchants never paid

All need joins.

Ask: how many of you write JOINs every day? Has anyone wondered HOW the database matches the rows?

Part 1

Nested Loop
a lookup per row

Step 1 in the lab guide

Nested Loop · Concept

For each outer row, find its inner rows

📞

For every payment, phone the merchant desk: "Who is M101?"

Fast if the desk has an index (directory). Slow if it reads the whole list each time.

Take next payment (outer)
▼
Find matching merchant(s) (inner)
▼
Output the pair
↺ repeat for every outer row

Without an index: outer rows × inner rows comparisons (4 × 3 = 12; 1M × 2,000 = 2 billion). With an index on the inner side: outer rows × a few pages.

Click Next. Without an index, every payment is compared with every merchant.

Run it with the index OFF: 12 comparisons. Reset, switch index ON: 4 direct lookups. Ask: what happens with 1 million payments and 2,000 merchants without an index?

Step 1 · Puzzle

103 payments, but only 102 rows. Why?

SELECT count(*)               AS payments,
       count(t.payee_account) AS with_payee
FROM transactions t
WHERE t.payer_account = 'u1000@bank';

--  payments | with_payee
--       103 |        102
One payment is PENDING with no payee yet (NULL).
An inner join keeps only rows that match, and NULL matches nothing.
Remember this NULL. It comes back in Step 8 as a trap.

Let the room guess before revealing. Typical guesses: duplicate, merchant missing. Real reason: NULL payee.

Part 2

Hash Join
build once, look up fast

Step 2 in the lab guide

Hash Join · Concept

Think: Python dictionary

# ① BUILD: read the small table once
merchants = {"M101": "Grocery",
             "M102": "Travel",
             "M103": "Food"}

# ② PROBE: read each payment once
for t in payments:
    category = merchants[t.payee]
① Buildsmall table → memory lookup table (Hash node)
▼
② Probeeach big-table row → one quick lookup
Each table is read only once. No index needed.

Freshers who know Python dicts get this immediately. A hash table puts each key into a "bucket" computed from the key, so lookups don't need to search the whole list.

Try it · Hash Join

Build the buckets, then probe them

Merchants (build)

Payments (probe)

Hash table: 3 buckets

Output

lookups: 0
Phase ① Build: put each merchant into its bucket.

3 build steps + 4 probe steps = 7 steps total, versus 12 comparisons for the plain nested loop. With 1M payments the difference is enormous.

Category totals over 1,000,000 payments

Read bottom-up: merchants scanned into the Hash (build), then each payment probes it. 998,018 rows, not 1,000,000: the 1,982 NULL payees match nothing.

Step 2 · Read the Hash node

Three numbers tell you if it fit in memory

FieldValueMeaning
Buckets2048Slots in the lookup table
Batches1Whole table fit in memory: good
Memory Usage119kBSize of the lookup table
Hash Join is the workhorse for large joins on =. Build from the smaller side.

Batches greater than 1 means a spill to disk. We'll provoke that on purpose in Step 9.

Merge Join
two sorted lists

Step 3 in the lab guide

Merge Join · Concept

Sort both sides, then walk forward together

🧾

Two queues, both sorted by merchant. Compare the two fronts:
• equal → output a pair
• smaller one → step it forward

Sort payments by payee
+
Sort merchants by account
▼
Walk both lists once, in step

The walk itself is very cheap. The cost is the SORT, unless an index already provides sorted order.

Summary

Which join wins when?

MethodWins whenWatch for
Nested LoopFew outer rows + index on inner sideHuge loops= with no inner index
Hash JoinBig joins on =, one side fits in memoryBatches > 1 (spill)
Merge JoinBoth sides already sorted (e.g. by index)Big Sort, external merge
You don't choose the method. You give the planner good indexes and fresh statistics.

Part 4

Foreign keys
are not indexed

Step 4 in the lab guide

Step 4 · Predict

Is the foreign key column indexed?

=# \d transactions
 ...
Indexes:
    "transactions_pkey" PRIMARY KEY,
                        btree (txn_id)
Foreign-key constraints:
    "transactions_payee_fk" FOREIGN KEY
      (payee_account) REFERENCES merchants
    "transactions_payer_fk" FOREIGN KEY
      (payer_account) REFERENCES accounts
Top 5 CORPORATE customers in Hyderabad. Will PostgreSQL use an index on payer_account?
There is no such index. Foreign key ≠ index.

Read the Indexes section aloud: only the primary key. Many developers assume FKs are indexed. That's true in MySQL InnoDB, not in PostgreSQL.

Step 4 · See

Index the FK: Hash Join → Nested Loop

JoinPagesTime

Only 48 accounts match, so 48 index lookups beat scanning 1M payments. Same 5 result rows before and after. Rule: PostgreSQL indexes primary keys automatically, never foreign keys.

Correctness traps
fast but wrong

Steps 6–8 in the lab guide

Step 6 · The LEFT JOIN trap

Failed payments per merchant, all merchants

A · conditions in ON
FROM merchants m
LEFT JOIN transactions t
  ON t.payee_account = m.merchant_account
 AND t.status = 'FAILED'
 AND t.txn_ts >= '2026-03-31'
2,000
merchants listed ✅
B · conditions in WHERE
FROM merchants m
LEFT JOIN transactions t
  ON t.payee_account = m.merchant_account
WHERE t.status = 'FAILED'
  AND t.txn_ts >= '2026-03-31'
439
merchants listed ❌

Ask the room to predict before revealing. Then: where did 1,561 merchants go? Merchants with no failed payment get NULL in t.status; WHERE t.status = 'FAILED' removes them. The LEFT JOIN quietly became an inner join.

Step 6 · Why

WHERE runs after the LEFT JOIN

LEFT JOINmerchant with no failed payment → kept, t.status = NULL
→
WHERE t.status = 'FAILED'NULL ≠ 'FAILED' → row removed
→
1,561 merchantssilently missing
With LEFT JOIN, conditions on the right-hand table go in ON, not WHERE.

Step 7 · Predict

Which Pune merchants have been paid at least once?

A · JOIN + DISTINCT
SELECT DISTINCT m.merchant_account,
       m.merchant_name
FROM merchants m
JOIN transactions t
  ON t.payee_account = m.merchant_account
WHERE m.city = 'Pune';
B · EXISTS
SELECT m.merchant_account, m.merchant_name
FROM merchants m
WHERE m.city = 'Pune'
  AND EXISTS (
    SELECT 1 FROM transactions t
    WHERE t.payee_account = m.merchant_account);
Both return 193 merchants. Which one does less work? (First: CREATE INDEX idx_txn_payee ON transactions (payee_account);)

Step 7 · See

EXISTS stops at the first match

A:  HashAggregate  (... rows=193 loops=1)
      ->  Nested Loop  (... rows=97662 loops=1)
            ->  Index Only Scan using idx_txn_payee ... (... rows=483 loops=202)
    Execution Time: 22.200 ms

B:  Nested Loop Semi Join  (... rows=193 loops=1)
      ->  Index Only Scan using idx_txn_payee ... (... rows=1 loops=202)
    Execution Time: 0.659 ms
Semi Join

"Return the merchant once if any payment exists."

"Has at least one?" → EXISTS, not JOIN + DISTINCT.

A builds 97,662 rows only to throw duplicates away. B reads one index entry per merchant. ~33× faster, same 193 rows.

Step 8 · NOT EXISTS

Merchants never paid: an Anti Join

SELECT m.merchant_account, m.merchant_name
FROM merchants m
WHERE NOT EXISTS (SELECT 1 FROM transactions t
                  WHERE t.payee_account = m.merchant_account);
 Nested Loop Anti Join  (... actual time=6.073..6.176 rows=50 loops=1)
   ->  Seq Scan on merchants m  (... rows=2000 loops=1)

Step 8 · The NULL trap

NOT IN with a NULL is never true

SELECT 'merchant1'
       NOT IN ('merchant2', NULL);

-- result:  NULL   (not TRUE!)
❓

"Is merchant1 not in {merchant2, unknown}?"
SQL: "can't be sure; the unknown might be merchant1."

Query (real data)Rows
NOT EXISTS (no PENDING payment)155
NOT IN (… PENDING payees)0

payee_account has 1,982 NULLs (pending payments).

Do the one-liner first. Then the real-data proof. Same question, 155 vs 0: NOT IN silently returns nothing.

work_mem is per sort/hash step, per connection. Don't raise it server-wide to fix one query: 100 connections × several steps each adds up fast.

Spot a spill

Three phrases that mean "used the disk"

Hash

Batches: 8

Sort

external merge Disk: 28664kB

Buffers

temp read=… written=…

Fix the query first (fewer rows, better index). Raise work_mem only for that query, with SET LOCAL.

Cheat sheet

Join patterns to remember

SituationDo this
Join on a foreign key columnIndex the FK column
"Has at least one?"EXISTS → Semi Join
"Has none?"NOT EXISTS → Anti Join (never NOT IN on nullable)
LEFT JOIN + filter on right tablePut the filter in ON
Batches > 1 / external mergeSpill: reduce rows or raise work_mem locally

Avoid these

Common mistakes

  • Assuming foreign keys are indexed
  • Filtering a LEFT JOIN's right table in WHERE
  • NOT IN (subquery) on a nullable column
  • JOIN + DISTINCT to test existence
  • Leaving enable_hashjoin = off in a session
  • Thinking table order in FROM controls join order
  • Raising work_mem server-wide for one query
