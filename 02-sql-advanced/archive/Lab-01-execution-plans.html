An SQL query says what to return. The planner chooses how PostgreSQL will access, filter, join, group and sort rows.

Planner questions

Full scan or index? Parallel or single process? Hash or sort aggregation? Which operations first?

10 / 35   ·   READ

EXPLAIN vs EXPLAIN ANALYZE

Estimates and observations are different

EXPLAIN

Planner estimates only. Query is not executed.

EXPLAIN (ANALYZE, BUFFERS)

Executes query; reports measured time, actual rows, loops and buffer usage.

EXPLAIN SELECT * FROM lab01_transactions
WHERE payer_account='u1001@bank';

EXPLAIN (ANALYZE, BUFFERS) SELECT *
FROM lab01_transactions
WHERE payer_account='u1001@bank';

Safety: EXPLAIN ANALYZE executes writes, too. Wrap mutating experiments in a transaction and ROLLBACK.

15 / 35   ·   PLAN A

What does loops=3 mean?

Do not read “rows=10” as the total
Reported fieldInterpretation
Scan actual rows=10 loops=3~10 matching rows per participant × 3 = 30 total
Rows Removed by Filter=99,990~99,990 per participant × 3 = 299,970 rejected
Gather actual rows=30 loops=130 rows delivered to the query consumer

Important distinction

With multiple loops, PostgreSQL reports averaged actual rows per invocation. It does not mean only 10 rows existed.

17 / 35   ·   READ

BUFFERS: cache activity, not disk timing

Interpret the counters precisely
CounterWhat it tells you
shared hit=34093,409 shared-buffer accesses found the requested page in PostgreSQL’s shared cache
shared read=33 page accesses caused pages to be brought into PostgreSQL shared buffers
Heap Blocks: exact=30Bitmap heap scan visited 30 heap pages with exact matching tuple locations

Not a shortcut

A buffer hit is not a unique row or necessarily a unique page. A shared read does not prove a physical disk read: OS cache can satisfy it.

Why indexes are not always used

Selectivity matters
FilterApprox. matchesLikely planner consideration
payer_account = 'u1001@bank'30 / 300k (0.01%)Narrow lookup: index appealing
status = 'FAILED'15k / 300k (5%)Index or scan depends on cost
channel = 'APP'225k / 300k (75%)Full scan may win
status IN ('SUCCESS','FAILED')300k / 300k (100%)Index often unnecessary

A filter matching many rows can make random heap access more costly than scanning sequentially.

Ask: Which node reads the most rows? Is a time-range index worth testing? Why might the answer depend on selectivity?
